Decide, from the evidence in $EVIDENCE only, whether this release is fit to be certified. You don't run tests, build anything or execute kernel code: every run already happened, without secrets, in earlier jobs.

THE EVIDENCE ($EVIDENCE)
- delta.json: the merged pull requests between v$PREV and v$VERSION. Each row has the PR number, its title, its kind (fix, feat, perf, revert, ci, chore, docs, test, other), whether it is a behaviour change, and the integration test files and test titles it added or changed.
- findings.json, computed in code from the runs below:
  - rows: one per pull request, with a decision. negative = a fix whose tests pass on v$VERSION and fail on v$PREV's dist (the NEGATIVE holds). passes = a feat or perf whose tests pass. no-negative = a fix whose tests also pass on v$PREV (a test gap). no-test = a behaviour change with no integration test. no-titles or not-run = tests whose titles the parser couldn't match or that didn't run. prev-not-run = the previous dist produced no result. fails-on-release = a test of this delta fails on v$VERSION. not-behaviour = CI, docs or dependency changes.
  - suites: v$VERSION's own test/integration suite on its published dist, compared test by test with v$BASE's suite on v$BASE's published dist (the certified release). regressed = passed on v$BASE, fails now. newFailing = a test new since v$BASE that fails. stillFailing = failed on both. fixed, removed, added and same are counts or lists.
  - findings: the list of everything above that needs judgement, plus missing evidence, plus compat-regression when kernel-compat reported regressions (read its report: the asset URL in compat.json, or the run's report job).
- release.json, prev.json, base.json: the raw per-test results (file, name, status, error), with logs in logs/.
- compat.json: homescoop's kernel-compat run on v$VERSION (the base set and catalog packages on this kernel), with its conclusion and, when attached, its verdict and regression count. found false means no run finished in time.
- known.json: issues every line carries while they are open.

WHAT TO DO
1. For every finding, read the rows and logs it points at, and the pull request (gh pr view <n> -R $REPO, gh api repos/$REPO/pulls/<n>/files) when you need the intent. Decide whether it is a real problem of v$VERSION, a test gap, or an artefact of the setup: a test that needs something CI doesn't have, a flake (it passes in the other run of the same file, or its error is a timeout unrelated to the change), or a test whose behaviour changed on purpose in the delta (say which pull request).
2. A suite regression explained by an intentional change in the delta isn't a regression; say which pull request changed it. One that isn't explained is a regression.
3. kernel-compat: a regression it reports for a base-set or catalog package is a finding of this release. A missing run is missing evidence, not a failure; say so.
4. Test gaps (no-test, no-negative) are known issues, never a FAIL by themselves: Lars's ruling is that every fix comes with an integration test that fails without it, so file a gap as an issue in $REPO that names the pull request and the behaviour-level test that would catch it.

Everything else is a known issue with a repro and the integration test that would catch it.

Otherwise gh issue create -R $REPO with the title, the repro (the failing test, its error, the run), the version, and the test that would catch it. Open issues labelled known-issue in $REPO and the ones in known.json are known issues of this release too when they still apply.
